# 校企合作课程设计方案

**合作单位**：杭州海康威视数字技术股份有限公司（萤石开放平台） × 杭州电子科技大学

## 一、课题名称

**基于海康威视硬件及萤石蓝海 AIoT 一站式工作台，开发无人健身房 SaaS 软件**

课程目标：

1. 让学生理解"硬件 + 云平台 + 业务 SaaS"的完整 AIoT 产品形态，认识海康威视门禁、门锁、摄像机等设备及萤石云开放能力。
2. 让学生经历一次完整的软件工程过程：需求梳理 → 架构设计 → 设备对接 → 双端开发 → 联调测试 → 上架交付。
3. 让学生掌握用 AI 对话式编程（萤石蓝海 AIoT 一站式工作台）提升开发效率的方法，同时具备审查、修改 AI 生成代码的能力。

## 二、课题内容详细介绍

### 2.1 业务背景

无人健身房（24 小时自助健身房）的核心是"无前台、无店员"：顾客线上预约并付费，到店自助开门，健身结束自助离场结算；商家远程管理多家门店的设备、订单和顾客。它的成立依赖三类能力：

| 能力 | 说明 | 本课题对应 |
|------|------|-----------|
| 身份与通行 | 只有已预约、已付费的顾客能进门 | 人脸门禁一体机或智能锁（二选一）+ 扫码开门 |
| 现场感知 | 店内是否有人活动、是否有异常进入，事后可追溯 | C6C 摄像机（直播预览、录像回放、人形检测告警） |
| 环境联动 | 有人开灯开空调，无人自动关闭节能 | 三方灯控器 / 智能开关 / 继电器 |

### 2.2 角色与需求梳理

**顾客（小程序端）**

| 模块 | 核心功能 |
|------|---------|
| 账号 | 微信授权登录、手机号绑定、实名/人脸采集（需单独授权同意） |
| 门店 | 门店列表（距离、营业状态、当前在场人数）、门店详情（器械、价格、实时空闲度） |
| 预约 | 选择门店 → 日期 → 时段，查看剩余名额，下单支付（课程内可用模拟支付） |
| 通行 | 获取入场凭证：人脸（自动下发至门禁）/ 临时密码 / 扫码开门 |
| 使用 | 在店计时、续时、"结束锻炼"按钮 |
| 结账 | 离场自动结算，超时补缴、提前离场规则展示，电子账单 |
| 我的 | 订单记录、健身时长统计、会员卡/次卡、信用分（爽约记录） |

**商家（Web 后台）**

| 模块 | 核心功能 |
|------|---------|
| 门店管理 | 新建门店、营业时间、容量上限、时段规则、价格策略（时段价/次卡/月卡） |
| 设备管理 | 设备添加/绑定到门店、在线状态、电量（门锁）、实时视频预览、录像回放、远程开门、灯控开关、人形告警记录 |
| 订单管理 | 预约单、消费单列表，状态筛选，退款/补缴处理，异常单（超时未离场、爽约） |
| 顾客管理 | 顾客档案、到店记录、消费总额、黑名单、人脸/凭证权限状态 |
| 运营规则 | 宽限时间、超时计费、爽约扣分、自动关灯延迟等参数配置 |
| 数据看板 | 每日总结：营收、顾客数、时段客流、设备健康、异常事件 |

### 2.3 硬件选型与整体设计

**推荐硬件清单**

| 类别 | 推荐型号 | 作用 | 对接方式 | 建议数量 |
|------|---------|------|---------|---------|
| 门禁（与门锁二选一） | 海康人脸识别门禁一体机 **DS-K1T6QT-F72MW**（国内标配） | 顾客刷脸进/出门，产生通行事件；配合扫码远程开门 | 萤石云接入 + ISAPI 协议透传（人员、人脸、远程开门） | 每组 1 台，或全班共享 2–3 台 |
| 门锁（与门禁二选一） | 萤石智能锁 **CS-LT70F-V100-C1CP-BK**（Wi-Fi 联网） | 临时密码开门、远程开锁，产生开锁事件 | 萤石 SaaS 智能锁组件 API | 每组 1 把，或共享 |
| 摄像机 | 萤石 **C6C Wi-Fi 摄像机** | 店内直播预览、录像回放、人形检测告警（不做人数统计） | 萤石开放平台直播、回放、告警消息 | 每组 1 台 |
| 灯控（三方） | 涂鸦等品牌智能开关，或 HTTP/MQTT 网络继电器 | 开关灯 / 空调 / 风扇等联动 | 三方云 API | 允许用 Mock 服务替代 |

**门禁与门锁怎么选**

| 方案 | 适用场景 | 通行方式 | 特点 |
|------|---------|---------|------|
| 方案 A：门禁一体机 | 商场、写字楼内门店，玻璃门或已有电控锁的门 | 刷脸 + 扫码开门，可进出双向管控 | 体验好，离场时间可精确获取；需配套电控锁（磁力锁/电插锁）、电源和出门按钮，安装较复杂 |
| 方案 B：智能锁 | 社区底商、独立门面的普通单开门 | 临时密码 + 扫码远程开锁 | 安装简单、成本低；通常只记录进门，离场时间需靠小程序"结束锻炼"或摄像机推断 |

课程中每组选定一种方案完成全流程，设备适配层需抽象出统一接口，便于答辩时说明另一种方案如何切换。

> 建议由海康侧统一提供教学套件并预先完成设备上云，避免学生在配网阶段耗费过多课时。各型号支持的具体开放能力以萤石开放平台文档和设备说明为准。

> C6C 只提供"有没有人在活动"的人形告警，不能给出店内人数。课程中"店内有多少人"一律由通行记录（入场 − 离场）计算，摄像机用于辅助判断和事后回放核查。

**整体架构**

```
┌──────────────────┐      ┌──────────────────┐
│  顾客端 微信小程序  │      │  商家端 Web 后台   │
└────────┬─────────┘      └────────┬─────────┘
         │ HTTPS                    │ HTTPS
         ▼                          ▼
┌─────────────────────────────────────────────┐
│              业务后端（学生开发）                │
│ 预约/订单 · 凭证管理 · 计费结算 · 规则引擎 · 报表 │
│ 设备适配层：萤石 Adapter ｜ 灯控 Adapter ｜ Mock │
│ 定时任务：凭证下发/回收 · 超时检测 · 日报生成      │
└───────┬──────────────────────┬───────────────┘
        │ OpenAPI / 消息推送     │ 三方 API
        ▼                      ▼
┌──────────────────┐   ┌───────────────┐
│ 萤石云开放平台      │   │ 三方灯控云/继电器│
│ 设备接入·SaaS组件   │   └───────┬───────┘
│ 直播·告警·消息订阅  │           │
└───────┬──────────┘            │
        ▼                       ▼
  门禁一体机或智能锁 / C6C 摄像机     灯 / 空调
```

设计要点：业务后端必须有"设备适配层"，所有硬件调用通过统一接口（如 `openDoor()`、`grantCredential()`、`revokeCredential()`、`switchLight()`），底层可切换真实设备或 Mock。这样没有硬件的时间段也能开发和测试。

### 2.4 顾客流程

```
线上预约 ──► 支付 ──► 凭证下发 ──► 到店开门 ──► 使用设备 ──► 离场 ──► 结算
```

| 步骤 | 顾客动作 | 系统动作 |
|------|---------|---------|
| 1. 线上预约 | 选门店、日期、时段 | 校验时段余量，锁定名额（未支付 15 分钟自动释放） |
| 2. 支付 | 支付预约费/扣次卡 | 订单状态 → 已预约 |
| 3. 凭证下发 | 首次使用需授权并上传人脸 | 预约开始前 N 分钟，后端向门禁下发人脸权限（有效期 = 预约时段 + 宽限），或生成临时密码 |
| 4. 扫码开门 | 到店扫门口二维码 / 刷脸 | 扫码：后端校验预约有效 → 调用远程开门；刷脸：门禁本地比对开门，事件推送到后端 |
| 5. 使用设备 | 健身 | 记录入场时间；联动开灯；C6C 人形检测告警确认店内有人活动 |
| 6. 离场 | 刷脸出门 / 点"结束锻炼" | 记录离场时间；在场订单清零且 C6C 连续 N 分钟无人形告警后，延迟关灯 |
| 7. 结账 | 查看账单 | 按实际时长与规则结算（超时补缴/提前离场），回收门禁权限 |

### 2.5 商家流程

```
开店配置 ──► 设备上云与绑定 ──► 价格与规则配置 ──► 日常运营监控 ──► 订单/顾客处理 ──► 每日总结
```

1. **门店管理**：创建门店，设置营业时间、容量、时段粒度（如 30 分钟）。
2. **设备管理**：在萤石平台添加设备后，在后台将设备绑定到门店并标注用途（入口门禁、出口门禁、店内摄像机、灯控）。
3. **规则配置**：价格、宽限、超时计费、爽约规则、自动关灯延迟。
4. **运营监控**：设备在线状态、实时视频与录像回放、告警（门未关、无预约时段人形告警、设备离线）、远程开门/开灯。
5. **订单与顾客管理**：查看订单、处理异常单、拉黑恶意顾客。
6. **每日总结**：查看当日账单、顾客数、客流时段分布、设备健康度。

### 4.2 验收场景一：模拟一次完整的无人健身房消费

按以下步骤逐项验收：

- [ ] 小程序登录，选择门店与时段完成预约和支付
- [ ] 预约开始前，后台按所选方案自动下发凭证（方案 A：向门禁下发人脸；方案 B：为智能锁生成临时密码），后台可查看下发状态
- [ ] 到店扫码或刷脸开门成功；未预约人员刷脸/扫码被拒绝
- [ ] 开门后灯控联动开灯，后台记录入场时间
- [ ] 商家后台可看 C6C 实时画面，能回放本次消费时段的录像，并收到人形检测告警
- [ ] 顾客离场（刷脸出门或点"结束锻炼"），系统按实际时长结算，生成电子账单
- [ ] 在场订单清零后延迟自动关灯，门禁权限 / 临时密码被回收
- [ ] 演示至少一种异常：超时补缴 / 迟到 / 爽约 / 设备离线兜底

### 4.3 验收场景二：商家每日总结

系统在每日营业结束后（或手动触发）生成当日总结，商家后台可查看，并进行PPT内容展示。至少包含：

| 维度 | 指标 |
|------|------|
| 账单 | 当日营收、订单数、客单价、退款金额、超时补缴金额、按支付方式汇总 |
| 顾客 | 当日到店顾客数（去重）、新客数、回头客数、爽约人数 |
| 设备 | 设备在线率、离线/告警次数、门锁电量预警 |
| 异常 | 超时未离场、推断离场单数、无预约时段人形告警次数（疑似闯入）、开门失败 |

## 五、可能遇到的问题

### 5.1 萤石蓝海 AIoT 一站式工作台使用介绍

**是什么**：萤石推出的 AI 驱动 IoT 应用开发平台。官方介绍是通过对话式编程快速生成 IoT 应用代码，并支持一键打包部署，让开发者把精力放在业务本身；官网首页的宣传口径是最快几十分钟完成一个 IoT 应用开发。

**入口与资料**

| 资源 | 地址 |
|------|------|
| 蓝海 AIoT 一站式工作台 | https://ai.ezviz.com |
| 萤石开放平台官网 | https://open.ys7.com |
| 开放平台 API 文档中心 | https://open.ys7.com/help |
| SaaS 组件 API 文档（智能锁、消息订阅等） | https://open.ys7.com/saas/openapi/zh/ |
| 官方开源 SDK（播放器、各语言 SDK） | https://github.com/Ezviz-OpenBiz ｜ https://gitee.com/Ezviz-OpenBiz |

**推荐使用方式**

1. 用萤石开放平台账号登录工作台（与萤石云视频 App 账号体系一致），确认已绑定课程设备。
2. 先用对话生成"骨架"：例如"生成一个微信小程序，包含门店列表、时段预约、我的订单三个页面"，"生成一个商家后台，展示设备列表并支持直播预览和远程开门"。
3. 每次只让 AI 完成一个功能点，生成后阅读、运行、修改，再进入下一个功能点。业务规则（计费、状态机）建议学生自己设计后再让 AI 实现。
4. 把有效的提示词记录在仓库 `docs/prompts.md` 中，作为结业文档的一部分。

> 注意：工作台当前有开发者积分类活动，额度与规则以官网为准；建议海康侧为课程统一申请教学账号/积分，并提供工作台操作手册或演示视频。

### 5.2 预约系统如何与门禁 / 门锁打通

核心思路：**预约是"权限"的来源，设备只是"权限"的执行者**。后端在合适的时间把"某人在某时段可以进某门"下发给设备，到期再收回。

**① 三种通行凭证的选择**

| 凭证 | 实现方式 | 优点 | 注意点 |
|------|---------|------|--------|
| 扫码开门 | 顾客扫门口二维码 → 小程序请求后端 → 后端校验预约 → 调用远程开门 | 不需要提前下发，实时校验，最易实现 | 依赖网络，需防重放（二维码含门店+门 ID，后端校验用户身份与时间窗） |
| 人脸 | 后端提前向门禁下发人员 + 人脸 + 有效期 | 体验最好，断网也能本地开门 | 下发是异步的，需要提前下发并确认结果；人脸属敏感个人信息 |
| 临时密码 | 后端为智能锁生成有时效、有次数的密码 | 无网络/手机没电时兜底 | 单把锁临时密码数量有限，需要池化与回收 |

**② 时序（以人脸为例）**

```
顾客        小程序        业务后端                 萤石云              门禁设备
 │ 预约+支付 │             │                       │                   │
 │─────────►│───下单──────►│ 订单=已预约             │                   │
 │ 授权+拍照 │───上传人脸───►│ 存储人脸URL            │                   │
 │          │             │                       │                   │
 │          │   [定时任务：预约开始前30分钟]          │                   │
 │          │             │──下发人员+人脸+有效期──►│──────透传────────►│
 │          │             │◄─────返回"下发中"──────│                   │
 │          │             │◄────权限同步消息推送────│◄────下发结果───────│
 │          │             │ 凭证状态=已生效          │                   │
 │ 到店刷脸  │             │                       │                   │──本地比对开门
 │          │             │◄──────开门事件推送──────│◄──────事件─────────│
 │          │             │ 记录入场、联动开灯        │                   │
 │          │   [离场或时段结束+宽限]                │                   │
 │          │             │──────删除人员权限───────►│──────透传────────►│
```

**③ 相关接口（以官方文档为准）**

以下"智能锁"接口对应方案 B（CS-LT70F-V100-C1CP-BK），"门禁一体机"对应方案 A（DS-K1T6QT-F72MW）。

| 能力 | 接口 / 说明 |
|------|------------|
| 获取 accessToken | `POST https://open.ys7.com/api/lapp/token/get`（appKey + appSecret），有效期 7 天，后端缓存复用，不要频繁获取 |
| 智能锁 · 添加 70F 锁 | `POST https://open.ys7.com/api/component/saas/res/device/lock/add`，参数 `deviceSerial`、`validateCode`。官方文档标题即"智能锁网关及 70F 智能锁添加"；锁需先完成 Wi-Fi 配网 |
| 智能锁 · 临时密码添加 | `POST https://open.ys7.com/api/component/saas/smartlock/tmppwd/add`，参数含 `beginTime`、`endTime`、`tmpPwd`（6 位数字）、`tmpPwdNum`（可用次数）；单把锁最多 5 组临时密码；文档注明使用时须先在锁上输入 `67#`，需在小程序里提示顾客 |
| 智能锁 · 临时密码修改/删除/查询 | `.../smartlock/tmppwd/update`、`.../smartlock/tmppwd/delete`、`.../smartlock/tmppwd/list/page` |
| 智能锁 · 透传人脸权限下发/删除 | `POST https://open.ys7.com/api/component/saas/smartlock/person/face/add`，参数 `employeeNo`（建议 32 位 UUID）、`faceImageUrl`、`extension.beginTime/endTime`；返回 `code=10` 表示下发中。删除用 `.../smartlock/person/face/delete` |
| 智能锁 · 远程控制 | `POST https://open.ys7.com/api/component/saas/smartlock/remote/door`，`cmd=open/alwaysOpen/resume` |
| 门禁一体机（方案 A）· 人员/人脸/远程开门 | 通过萤石开放平台的 ISAPI 协议透传能力调用设备标准 ISAPI，如人员 `/ISAPI/AccessControl/UserInfo/Record`、人脸 `/ISAPI/Intelligent/FDLib/FaceDataRecord`、远程开门 `/ISAPI/AccessControl/RemoteControl/door/{id}`；透传入口与鉴权方式请查阅开放平台文档中心 |
| 事件推送 | SaaS 消息订阅：提交 `postUrl` 后平台以 JSON 推送 RSA 加密消息，用订阅公钥解密；消息类型包括门禁&锁事件 10004、设备上下线 10006、门禁权限同步 10007 等 |

SaaS 组件接入前置步骤（官方接入流程）：注册开放平台账号获取 appKey/appSecret → 提交工单开通 `saas_online` 消息管道 → 在商业智居平台（https://es.ys7.com）注册并创建企业、填入 appKey/appSecret → 调用组件接口并对接消息推送。建议海康侧提前为课程账号完成开通。

**④ 实现要点**

1. **提前下发 + 结果确认**：人脸下发是异步的，至少提前 15–30 分钟下发；以权限同步消息或查询接口确认成功，失败自动重试，最终失败时降级为扫码/临时密码并通知顾客。
2. **有效期写进设备**：下发时就设置 `beginTime = 预约开始 - 提前入场宽限`、`endTime = 预约结束 + 离场宽限`，即使后端宕机，设备也不会长期放行。
3. **到期必回收**：定时任务扫描已结束订单，删除人员权限/临时密码；同一顾客有连续预约时合并有效期，避免反复增删。
4. **临时密码池化**：单锁最多 5 组，按"同时段在场人数"分配索引，用完立即删除；密码随机生成，不可复用。
5. **人员 ID 映射**：顾客 ID ↔ 设备 `employeeNo` 建立映射表，设备侧不存手机号、姓名等明文信息。
6. **幂等与补偿**：所有下发/删除请求带业务单号，可重复执行；设备离线时进入补偿队列，上线消息到达后重放。
7. **合规**：人脸采集须单独授权同意，说明用途与保存期限；提供"删除我的人脸"功能；人脸图片 URL 使用带时效的私有链接。

### 5.3 如何管理顾客实际时间与预约时间的差异

无人场景没有店员催促，必须靠**规则 + 事件**自动处理。先定义几个时间点：

```
      提前入场宽限        预约时段            离场宽限
  ├──────────────┼══════════════════┼──────────────┤
  T0-15min       T0（开始）         T1（结束）     T1+10min
        ▲               ▲                 ▲              ▲
     最早可进门      迟到判定起点        计费终点      超时判定起点
```

**① 实际入场 / 离场时间怎么取**

| 时间 | 优先级（高 → 低） |
|------|-----------------|
| 实际入场 | 门禁刷脸/扫码开门事件（方案 A）或智能锁开锁事件（方案 B） → 小程序"开始锻炼" |
| 实际离场 | 门禁出门刷脸/扫码事件（方案 A） → 小程序"结束锻炼" → C6C 连续 N 分钟无人形告警（推断无人） → 营业结束兜底 |

方案 A 建议出门也刷脸或扫码，离场时间最准确；方案 B 的智能锁一般只记录进门，离场主要依赖小程序"结束锻炼"和摄像机推断，计费规则要对"推断离场"留出复核空间。

**② 差异场景与处理规则（商家可配置）**

| 场景 | 判定 | 建议规则 |
|------|------|---------|
| 提前到店 | 入场时间 < T0 | 宽限内允许进门，不额外计费；宽限外无法开门，小程序提示"可提前 15 分钟入场" |
| 迟到 | 入场时间 > T0 | 结束时间不顺延，按原预约计费；超过 N 分钟未到，名额可释放给他人（权限保留到 T1） |
| 爽约 | T1 时仍无入场记录 | 不退款或部分退款，记爽约一次，累计 3 次限制预约 |
| 提前离场 | 离场时间 < T1 | 按次/时段计费时不退；按分钟计费时按实际时长，最低消费保底 |
| 超时 | 当前时间 > T1 + 宽限且未离场 | T1 前 10 分钟小程序提醒续时；超时按分钟计费并设封顶；下一时段已满员时优先保证下一位顾客 |
| 忘记离场 | 有在场订单未离场，但 C6C 连续 N 分钟无人形告警 | 以最后一次人形告警时间为离场时间，订单标记"推断离场"，商家可调回放复核 |
| 疑似闯入 / 尾随 | 无在场订单时出现人形告警 | 告警推送商家，商家通过直播或回放核查；确认后对相关时段开门者记风险。C6C 不统计人数，"一人开门多人进入"无法自动识别，靠回放抽查 |
| 设备离线 | 开门事件未到达 | 以设备恢复后的补推事件为准；扫码开门以后端调用成功时间为准 |

**③ 落地建议**

1. **订单状态机**：`待支付 → 已预约 → 已入场 → 使用中 → 已离场 → 已结算`，支线 `已取消 / 爽约 / 超时待补缴 / 推断离场`。每次状态变化记录触发事件来源，便于对账。
2. **超时补缴**：可要求预约时绑定次卡余额或押金，超时金额自动扣除；课程中用余额模拟即可。
3. **计费规则配置化**：宽限分钟数、超时单价、封顶金额、爽约阈值都放在门店规则表，不要写死在代码里。
4. **定时任务**：每分钟扫描"即将结束""已超时""应回收权限"的订单，驱动提醒、计费和权限回收。

### 5.4 其他需提前确认的事项

| 事项 | 风险 | 建议 |
|------|------|------|
| 小程序上架主体 | 个人主体小程序无法使用微信支付，部分类目需企业资质 | 课程统一用模拟支付；上架主体由海康或学校提供，或至少发布体验版 |
| 设备数量 | 硬件少、组数多，排队调试 | 设备适配层支持 Mock；实验课按组分时段使用真机 |
| 平台开通 | SaaS 组件、消息管道需工单开通 | 开课前由海康侧统一开通并验证 |
| 回调地址 | 消息推送需要公网可访问的 `postUrl` | 提供统一的云服务器或内网穿透方案 |
| 数据安全 | appSecret、accessToken 泄露 | 只放在后端，禁止写入小程序/前端代码和公开仓库 |
