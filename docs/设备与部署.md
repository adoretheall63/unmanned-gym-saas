## 3. 最先完成的三个动作

### 动作一：和老师/企业对齐，而不是先买设备

可直接使用下面的沟通提纲，由组长自行发送或当面询问：

> 我们准备按预约、凭证、开门、视频、结算、日报完成闭环。请确认：
> 1. 最终与阶段截止日期？小程序体验版、模拟支付、Mock 灯控是否按方案认可？会员卡、信用分、多租户是否必考？
> 2. 本组能拿到哪种门禁/门锁、C6C 和配套安装件？设备何时可用、能使用几次、现场谁协助？
> 3. 是否提供已绑定设备的萤石课程账号、蓝海额度、SaaS 组件和 saas_online 消息权限？能否给一个真实接口和回调样例？
> 4. 是否提供小程序主体/AppID、管理员协助、服务器及 HTTPS 域名？如不提供，哪些需要我们自行申请？
> 5. 教学硬件若暂不可用，Mock 阶段和最终真机验收分别怎么认定？

### 动作二：全组开一次 30–45 分钟启动会

每人说清技能、时间、可到场时段；共同看验收流程，确定一名组长、一名集成发布负责人和各模块负责人。确定唯一仓库、任务记录位置、每周联调时间。每个任务必须有负责人、期限、产物和验收方式，不能只写“负责前端”。

### 动作三：尽早做两个最小探针

1. 手机探针：实际 AppID 的小程序体验版，通过手机网络访问一个已部署的 HTTPS 接口。用它尽早暴露账号、成员权限、域名和部署问题。
2. 硬件探针：用课程账号对真实设备执行一次所需操作，收到一次真实事件；C6C 另验证预览、回放、告警。保存脱敏请求、响应、时间和设备现象。

某个探针受阻时，明确记录缺哪项、由谁联系、预计何时解决；软件可以先用 Mock，但真实设备能力不能标为完成。

前端初版先保证预约和设备流程可用，沿用生成工程已有组件和结构，不额外引入动画、复杂图表或第二套 UI 框架。你主要提供稳定接口和联调支持，不默认接手两端页面。

组长负责集成节奏，但每人都要测试自己的功能并参与一次完整现场演示。指定一位备份操作者，避免只有管理员或某个同学到场时才能演示。

## 5. 硬件选型先看可验证能力

优先选择企业已提供且已验证课程 API 的套件，不单凭文档推荐型号采购。

| 选择 | 开工前必须实测 | 会影响什么 |
|---|---|---|
| 门禁一体机 | 指定设备是否支持所需云透传；人员/人脸下发、有效期、删除；一次真实开门和事件；出门方向能否识别 | 若只有入口事件，不能宣称已实现双向精确计时；可能还需出口读头或其他配套 |
| 智能锁 | 此型号及固件能否创建/查询/删除临时密码、远程开锁、接收开锁事件；密码容量和使用步骤 | 并发预约必须受凭证容量约束，不能接单后才发现无密码可用 |
| C6C | 实时画面、指定时间段回放、人形告警；存储和服务权限是否齐全 | 没有录像存储不能只靠播放器实现回放；无告警不代表无人 |
| 灯控 | 是否有真机、控制协议和用电安装条件 | 教学初版可 Mock；真机优先安全的低压演示负载，由有资质或课程指定人员接线 |

实测顺序：查清账号绑定 → 在官方工具确认设备在线 → 单独 API 调用 → 回调接收 → 接到业务订单。一次只让一组执行门锁/凭证变更，避免共享设备权限被另一组覆盖。

萤石 SaaS 官方概述要求设备增删改查走对应基础组件接口，避免与普通开放平台设备管理接口混用造成数据不一致。组件使用说明还列出了创建企业关联 appKey 和申请 saas_online 消息管道的前置条件。课程账号是否已完成，仍须企业确认。

## 6. 小程序申请、开发和体验版路线

先确定账号归属，再申请。优先询问学校/企业是否已有可用主体和 AppID；不要未经协调把团队交付长期绑在某个同学的私人账号上。

1. 账号负责人进入微信公众平台 `https://mp.weixin.qq.com/`，核对是否已有小程序。若没有，按后台当前流程注册；先确认主体、管理员和用途，再填资料。
2. 在后台确认 AppID、成员权限及当前要求的名称、类目、主体校验、备案和隐私信息。不同交付路径的具体条件以后台为准，不能把“注册成功”当作“可以正式上线”。
3. 管理员添加实际开发人员；将组员、指导老师和用于验收的账号加入相应体验范围。管理员保管账号，开发者不靠共享管理员密码工作。
4. 开发者在 Mac 安装并登录微信开发者工具，以真实 AppID 导入或创建项目。先做最小页面、登录链路和网络请求；测试号仅用于前期实验，不替代目标 AppID 验证。
5. 后端先提供稳定的 HTTPS API 域名；按实际请求配置服务器合法域名，需要上传/下载时分别配置相应域名。不要把 Mac 的 localhost 或局域网地址写成正式 API 地址。
6. 首次即上传一个最小版本，在后台设置体验版，由另一位体验成员使用手机蜂窝网络打开并请求接口。验收时按正常平台校验运行，不靠开发工具“忽略域名校验”证明部署成功。
7. 每个里程碑更新体验版并记录版本、提交和后端环境。公开小程序码与本系统的门店/门二维码是不同用途，不能混用。
8. 若要求正式发布，预留资料完善、提审、退回修改和再次审核时间；确认后台所有要求满足后再提审。审核通过后仍须执行发布，发布后再做手机验收。

模拟支付在界面明确显示，不接真实扣款。若后续改为真实支付，单独核实商户主体、支付权限、结算、退款和回调要求，并重新估算工作量。

微信登录、手机号绑定、人脸采集是三件事，不要假定一次微信登录自动获得手机号或实名信息。手机号相关权限/费用由实际主体后台核实；非验收必需时先不把它设为预约的前置条件。人脸方案仍需独立授权和数据删除流程。

以上微信步骤是待实操核对的操作路线；本轮官方开发文档页面未能成功抓取，没有核验你们主体的实时申请条件、费用和具体菜单。

## 7. 部署：把“服务器在哪”变成能验收的事实

先核实蓝海实际能生成什么工程、能否导出源码、是否提供数据库/后端常驻运行、定时任务、公网 HTTPS 和外部回调。宣传中的“一键部署”不能替代这些检查。若工作台环境满足要求，直接使用；否则向老师确认工作台生成并导出源码、再部署到学校/企业服务器是否符合课程要求。

资源优先顺序：学校/企业现有环境 → 工作台满足要求的托管环境 → 团队确认费用后自行准备。先不购买云服务器或域名。

外部服务器路线采用一个应用进程、数据库和 HTTPS 入口即可，不引入微服务或 Kubernetes。Redis已纳入技术选型，不引入消息队列；对象存储按实际文件需求配置；人脸数据需要受控存储，不能为了省事暴露为永久公开地址。

| 要准备的内容 | 负责人实际要做 | 验收 |
|---|---|---|
| 服务器/运行环境 | 明确提供方、登录权限、CPU/内存/存储、到期日、后端运行方式 | 后端可启动并长期运行 |
| 域名与 HTTPS | 明确域名所有者、DNS 和证书管理；境内部署相关备案条件按服务商和平台核对 | 手机网络访问证书正常，无错误跳转 |
| 数据库 | 创建环境配置、初始化结构和演示数据，限制外部访问，安排备份 | 重启数据仍在；备份可恢复到测试环境 |
| 后台与 API | 部署 Web、设置 API 地址和鉴权、处理需要的跨域/反向代理 | 未登录被拒绝，正常登录可操作 |
| 萤石回调 | 提供稳定地址，按选定接口官方协议验证来源并解析消息，处理重试与重复 | 真实事件形成且只形成一次业务记录 |
| 定时任务 | 确认宿主支持，统一时间口径，保证进程重启后任务可恢复 | 到期撤权任务可执行，失败可见且能重试 |
| 凭据 | 后端保存微信和萤石密钥，前端只拿必要的受限数据 | 构建产物、仓库和日志没有泄露密钥 |
| 发布交接 | 记录版本、部署步骤、日志位置、备份与回滚方法 | 第二个人按说明能完成部署或恢复 |

临时穿透仅作获准后的短期联调备选，须核实微信域名校验及平台回调要求；地址变动、休眠和断网会影响验收，不能默认等同于稳定交付环境。


## 10. 最小但有意义的验收清单

- [ ] 两个用户抢最后一个名额，仅一人预约成功；未支付到期释放容量。
- [ ] 无预约、越过时间窗、其他门店/其他用户订单均不能开门。

## 11 Mock与萤石适配详细依据（历史资料核查）

下面保留接口核查、异步差异、企业问题清单和真机通过条件；它们是适配准备，不是已验收的设备能力。

核查日期：2026-10-21。当前硬件未准备就绪，先用 Mock 推进；本文整理接入契约和官方资料，不包含业务实现，也不代表课程账号已开通或真机已通过。

### 1. 当前实施路线

预约、订单、容量校验、模拟支付、计费、账单、日报和鉴权按真实业务实现。仅替换设备边界：下发/回收凭证、开门、设备状态、灯控、设备事件，以及视频展示的数据来源。

调用关系：小程序/Web → 业务服务 → 设备适配接口 → Mock 或萤石实现。

事件关系：测试事件入口或萤石回调 → 各自解析/验证 → 同一业务事件处理逻辑 → 更新凭证/设备/订单记录。

不在每个订单接口里散布 `if mock`，不让前端直接调用萤石，不先搭独立 Mock 微服务。用同一 Java 后端中的实现替换即可。只为实际开发的能力设置接口，不建通用 IoT 框架。

先固定业务侧契约，最终门禁/门锁型号确定后再实现供应商参数转换。统一契约不表示所有设备都支持同一种能力；未支持必须明确返回，不自动伪装成功。初版只开发老师最终认可的一种通行方案，不同时完成两套硬件驱动。

### 2. 最小契约：现在约定，编码时再确定 Java 类型

以下名称是本项目建议，不是萤石 API。

| 能力 | 业务输入 | 必须保留的输出/限制 |
|---|---|---|
| 下发凭证 `grantCredential` | 业务请求号、设备、内部用户映射、凭证类型、起止时间；人脸/密码仅按选定方案提供 | 待确认/生效/失败/结果未知；保存供应商凭证索引、命令标识等实际返回值 |
| 回收凭证 `revokeCredential` | 原凭证记录及设备；包含供应商索引/人员映射 | 待回收/已回收/失败/结果未知；请求超时不能直接当已删除 |
| 请求开门 `openDoor` | 请求号、设备；预约权限由业务层先校验 | 控制结果或结果未知；与设备开门事件、人员实际进场分开 |
| 查询设备状态 `getDeviceStatus` | 设备 | 在线/离线/未知，状态时间；电量可缺省，不能用 0 冒充未知 |
| 控制灯 `switchLight` | 设备、开/关 | 操作状态；先 Mock，后续按实际第三方协议接入 |
| 获取视频播放资料 | 摄像机、预览或回放、回放时间范围 | Mock 标识或真实播放参数、有效期；无录像和无权限要分别展示 |

本地记录至少保留：内部设备 ID、门店 ID、提供方及其设备标识；内部凭证 ID、关联订单/用户、有效期、状态、提供方返回的凭证/指令标识；操作请求与结果、事件发生/接收时间。不要把密码、人脸地址、token 等完整内容写入日志。

事件需要表达：设备在线/离线、凭证下发/回收结果、开门、有人形告警。保留来源 `MOCK` 或 `EZVIZ`、设备、发生时间、接收时间、厂商消息标识（若有）与原始事件类型；进出方向和用户身份允许未知，不能凭空生成。业务去重依据以实际厂商消息字段为准，不宣称平台必然提供 eventId。

本地业务请求号用于追踪和去重，不假定每个萤石接口都接收业务单号。请求超时后先查询或等待事件确认；不能把再次调用物理开门当作无副作用的安全重试。

### 3. Mock 必须覆盖的行为

| 场景 | 模拟行为 | 业务应看到的结果 |
|---|---|---|
| 正常凭证 | 请求先受理，再注入成功事件；允许在选定接口语义明确时同步成功 | 凭证按真实语义改变状态，订单支付不等于设备已生效 |
| 容量限制 | 智能锁临时密码测试档按文档 5 组限制；与门店人数分别管理 | 无凭证容量时拒绝/等待并有提示，不无限接单 |
| 设备离线 | 控制失败或等待处理 | 不显示开门成功，后台可见原因 |
| 请求超时 | 调用方不知道结果，随后可能到成功事件 | 结果未知，可确认或复核，不立即重复物理动作 |
| 重复事件 | 同一设备事件发送两次 | 不重复计费、入场或汇总 |
| 延迟/乱序事件 | 旧下发结果在取消/撤权后才到 | 不把已取消凭证直接恢复；记录并触发必要补偿 |
| 到期/回收失败 | 到期执行任务，首次回收失败，后续成功 | 状态可追踪，进程重启后仍可继续处理 |
| 开门与入场分开 | 只产生控制结果，不产生进场确认 | 不自动断言有人已进入；按约定的教学确认规则处理 |
| 视频 | 占位画面或明确标注的测试录像 | 显示“模拟视频”，不冒充摄像机实时画面 |
| 没有人形告警 | 不注入新事件 | 不据此认定无人、离场或自动扣费 |

手动注入事件入口只在开发/测试环境启用且有权限校验；真实环境不得由普通用户伪造开门或凭证成功事件。正常路径使用同一业务事件处理器，但 Mock 入口不能跳过真实回调所需的协议验证来证明真实接入完成。

Mock 行为优先手动选择成功、失败、超时、重复事件，便于复现；不需要随机故障引擎。开发时至少保留一组业务测试：重复事件只处理一次、取消后迟到的下发事件不能恢复有效权限、未知开门结果不自动确认进场。

### 5. 异步与回调：接入前先知道的差异

- [订阅创建](https://open.ys7.com/saas/openapi/zh/base/subscription/subscription_add.html)列出：10004 门禁/锁事件、10005 设备报警、10006 上下线、10007 门禁权限同步。某类型存在不代表 C6C 或所选锁必然通过该类型上报，必须取一次真实消息核对。
- [推送服务](https://open.ys7.com/saas/openapi/zh/base/subscription/servie.html)描述加密 body，解出后结构为 `eps.alert[]`，内含 `msgType` 和 `body`。解密示例所用公钥来自订阅详情；不能照常见“私钥解密”的通用模板猜协议。
- 订阅创建页称回调 2000ms 超时后重试 2 次，失败可查失败记录。建议先可靠保存已通过协议校验的事件，再迅速按平台要求应答，后续处理业务；应答格式及实际重试行为仍需联调核实。
- 文档描述 512 位 RSA 和公钥解密的历史协议。解密不能单独等同于可信来源证明；在接入前向企业核实当前协议、来源校验、密钥管理及是否有新版。不能自改算法导致与平台不兼容，也不把历史示例当作安全设计建议。
- [锁事件对照表](https://open.ys7.com/saas/openapi/zh/base/subscription/lock_event_list.html)区分密码、临时密码、人脸、中心开门等事件。保存原类型，映射到内部开门事件；不要推断所有开门事件都有可关联到订单的用户标识或出口方向。
- 人脸下发文档外层成功只代表进入与设备交互阶段；保存各 `operation` 的 `cmdId` 和状态，等待后续确认，不把外层成功直接显示为生效。同一设备的并发操作还应遵循该接口限制。[人脸下发](https://open.ys7.com/saas/openapi/zh/smartlock/2_14_face_add.html)

需记录的文档疑点：不同接口示例有 `200` 与 `saas-200`；人脸子结果示例有 `200`，说明又列 `1` 成功、`10` 下发中并提及未清晰列出的 `authorityStatus`；有效期格式文本和示例也不完全一致。用厂商确认及实测建立逐接口解析规则，不能仅判断 HTTP 200，也不能全局接受任意包含“200”的字符串。

### 6. C6C 视频与门禁一体机：分别准备

#### C6C：先在商家 Web 展示

已持有型号 CS-C6c（4WF，4mm），运行、绑定和录像尚未验证。先 Mock 摄像机状态、告警和视频占位，再单独完成真直播、录像回放、告警三项验证。视频先放在商家后台，顾客小程序初版不增加实时视频。

本轮查到 [EZUIKit-JavaScript 旧仓库](https://github.com/Ezviz-OpenBiz/EZUIKit-JavaScript)已声明停止维护并指向 [EZUIKit-JavaScript-npm](https://github.com/Ezviz-OpenBiz/EZUIKit-JavaScript-npm)。后者提供预览、SD 卡/云录像回放及框架示例，是后续播放器接入依据。接入时按当时稳定版本验证工程与资源加载，不照搬旧仓库脚本。

后端先做商家鉴权，再按实际授权方案提供播放器必需的受限凭据和播放参数；不得把 appSecret 或账号级主凭据直接交给浏览器。播放器可能需要 token，须核实可用的设备/权限范围和有效期控制，不能承诺前端完全不接触任何播放凭据。

不要把 SaaS 导航中的“云视频会议组件”误认为 C6C 视频接口；该页目前正文称暂未发布、需线下联系。[组件页面](https://open.ys7.com/saas/openapi/zh/cloudVideo/)

本轮未完整取得开放平台视频 API 的参数文档，因此不把网上常见直播 URL 路径或协议数字写成已核实接口。后续请企业提供当前视频接入文档入口、账户授权方式、播放/回放权限、流量与存储条件，以及一份该型号告警样例；录像存储和人形检测均须独立验证。

#### 门禁一体机：保留适配位置，暂不伪造真实请求

课程方案提出 ISAPI 透传，但本轮未核实最终型号的云透传入口、请求头、设备能力集和人员/人脸完整协议。现在只在业务契约中保留“凭证下发/删除、有效期、开门、事件”；向企业索取准确型号、当前授权的透传文档及一套可运行示例后再映射。锁的人脸组件接口不能作为门禁已支持的证据。

### 8. 从 Mock 切换到真机的通过条件

1. 企业账号、设备归属、接口权限和回调路由确认；先查询状态，不做初始化或其他清除权限的操作。
2. 选定一种硬件方案，依次验证一个凭证下发/查询/回收、一次开门、一个真实事件，记录脱敏响应和设备表现。
3. 将厂商结果映射到同一业务契约；用真实脱敏样例补充解析测试，复跑重复、超时和撤权失败场景。
4. 各设备按准备程度接入：例如摄像机先真接入、门锁和灯控暂 Mock。界面逐项标识来源，不能切一个总开关就宣称全真实。
5. 手机和公网环境重新完成消费流程，分别验证真直播、回放、告警。确认凭证到期/撤权结果，再登记“真机通过”。

这条路线能减少业务重写，但无法消除真机联调。Mock 完成不能证明所选设备支持课程功能，也不改变课程最终验收要求。
